# Recovery

State version 4 stores selected execution configuration, hook fingerprints and generations, expansion and restoration progress, refresh and merge checkpoints, and deferred-cleanup state. Configuration schema version 1 is a separate contract. Legacy manifests remain readable without writes. A ready legacy Change requires explicit baseline adoption through `vcm recover <change> --adopt-config` before mutation or upgrade. Inspect its `--dry-run` first. Interrupted legacy operations must finish with the previous binary before upgrading; preserve legacy synchronization journals until that recovery finishes.

Start with `vcm status <change>`. Keep selected repository names and Change paths intact while repairing an interrupted operation. State under the workspace Git common directory is local operational evidence, not an executable project artifact. Do not edit it to bypass ownership, configuration, or revision checks.

Selected repository paths, URLs, trunks, dependency order, inline hooks/order, and applicable runners are fingerprinted. External script contents are not hashed. New unselected configuration entries do not affect existing Changes. Removing a selected declaration or changing recorded execution configuration is reported through inspection and previews and blocks mutation until resolved.

Use `vcm recover <change> --adopt-config --dry-run` to inspect adoption, then omit `--dry-run` to record it. Adoption never executes hooks and cannot be combined with `--retry-hook`. It rejects rebinding owned repository identities, paths, URLs, or trunks; restore the recorded declaration instead. Dependency changes must preserve a complete selection and cannot change interrupted operation order. Pending or failed hook changes may be adopted. A running hook first requires the existing external-effects acknowledgment. Changed completed hooks in an unfinished phase are invalidated with subsequent hooks only if no downstream resource effect has occurred; otherwise restore recorded configuration. Completed creation phases remain historical and are not rerun retroactively. Completed hook evidence identifies the definition and generation that executed.

VCM serializes mutations with an operating-system workspace lock. If another invocation is active, let it finish. The lock is released when its process exits; the lock file may remain and should not be deleted to bypass an active lock.

For a failed hook, inspect stderr and the relevant Change checkout. Repair and commit intended output, ensure the checkout is clean, and retry the same command. Completed hooks remain skipped on retry; failed hooks run again unless their merge phase is deliberately omitted with `--skip-hooks`. An interrupted hook remains recorded as `running`. Inspect its external effects, then run `vcm recover <change> --retry-hook <repository/phase/id> --acknowledge-effects`. Recovery locks and reloads state, validates the exact hook and applicable lifecycle phase, and changes only that outcome to a retryable failure. It prints the original operation to rerun; it does not run the hook itself. `--dry-run` previews the acknowledgment. Do not edit ownership or revision fields. VCM does not promise exactly-once external effects.

Merge overrides are recovery decisions, not relaxed integrity checks. `--ignore-hook-failures` ignores only a clean lifecycle hook command's nonzero exit, records the failed outcome, and continues; it does not authorize cleanup or create a backup. Successful merge cleanup always removes Git-ignored content from owned Change worktrees after local integration is checkpointed, without requiring a VCM force flag. `--skip-hooks merge-before` or `merge-after` bypasses the configured phase for that invocation without recording completion, and `--skip-hook-git-hooks` suppresses repository Git hooks only for Git commands launched inside lifecycle hooks. Dry-run output reports all three choices and whether ignored content will be deleted. Configuration, state, hook output, tracked or staged modifications, ordinary nonignored untracked content, ownership, revision drift, foreign nested Git repositories, conflict, and incomplete create, refresh, merge, or drop failures still stop recovery. Preserve and inspect the workspace before retrying.

For an interrupted merge, inspect both the Change source and origin trunk. Completed downstream merges remain in place if a later hook or workspace merge fails. Retry the same Change after repairing the reported problem; do not reset completed targets or advance source branches behind the manager's recorded checkpoints. Unexpected source or target revisions require explicit investigation.

If a canonical local trunk advances, merge refuses to start and directs you to `vcm refresh`. Refresh never fetches. It validates all selected canonical checkouts, including configured-trunk branch and ownership, before changing state or any Change repository; an unrelated checked-out branch is rejected. Targets resolve from configured trunk refs and are revalidated before application. It checkpoints each selected repository, merges advanced local trunks in dependency order, preserves conflicts for repair, and resumes idempotently. If the canonical trunk advances again while a refresh is being repaired, resolve and commit the recorded conflict in the Change checkout without moving the canonical trunk backward. On retry, VCM recognizes a completed resolution commit, a recorded prepared merge commit, or a prepared index that matches the recorded merge tree; it finalizes that checkpoint and continues against the newer descendant canonical target in the same invocation. `vcm status --verbose` shows the recorded refresh target, current canonical target, and recognized recovery state.

Refresh still stops when completion cannot be proved: an unresolved merge, an unexpected Change revision that does not contain the recorded target, unrelated dirty worktree content, or a rewritten/non-descendant canonical target requires inspection and explicit repair. The error reports the recorded and current revisions when available; do not reset a safely advanced canonical trunk merely to match the old checkpoint. Run `vcm fetch` to update cached remote state and `vcm pull` to update canonical local trunks before refresh when remote synchronization is intended.

After ordinary integration, merge records `merge-finalizing` separately from completed repository removal. If cleanup is interrupted, retrying plain `vcm merge <Change Tag>` removes only resources whose removal is not checkpointed, including ignored content in retained owned worktrees; no `--force` flag or recovery backup is involved. If a `merge-after` hook fails after every worktree is gone, retry from a base repository; completed removals and hook outcomes are preserved, integration is not repeated, and only pending post-cleanup hooks run. Failed `drop-after` hooks are likewise resumed with `vcm drop <Change Tag>` from a base repository after the corresponding worktree has disappeared.

With `vcm merge <change> --keep`, retention is recorded before integration starts and survives retry without the flag. Completed integration remains active and navigable with cleanup pending. `vcm cleanup <change>` verifies source revisions and ownership, checks that integration commits remain reachable from configured trunks, and then removes owned worktrees and runs `merge-after` hooks. Safely advanced descendant trunks are allowed; rewritten targets, changed sources, dirty tracked/nonignored untracked contents, or ownership drift stop cleanup. Cleanup preserves ignored-content removal policy, resumes removals and hooks, and never reintegrates. Retained integrated Changes cannot be expanded, refreshed, republished, or merged again.

For interrupted `vcm add <change> --only api,web`, retry the same selection after repairing the failure. The complete addition set is journaled before resource creation. New children resume in dependency order; completed work and existing child hooks are preserved. Root `create-after` executes once per expansion generation using the expanded inventory. Normal or forced drop can remove partially expanded Changes subject to the normal ownership and backup rules.

For interrupted `vcm restore <snapshot-file> --name <slug>`, retry the same snapshot and name in the same bootstrapped workspace. Restore preserves exact source/base revisions, creates a new Change identity, and runs no lifecycle hooks. Missing objects require publication at the source and explicit `--fetch` if they are unavailable locally. Fetching uses matching configured origins, never a snapshot-supplied arbitrary URL. Snapshots omit hooks and recovery state; they do not replace operational journals or bundle Git objects. Dry runs report remote object availability as unverified.

`vcm fetch` changes only cached remote-tracking refs. `vcm pull` rejects dirty, non-trunk, or interrupted canonical checkouts before any rebase and blocks rebases that would rewrite an active Change baseline. If pull reports a rebase conflict, Git's interrupted rebase is intentionally preserved; resolve it with Git and continue, or abort it, before retrying VCM. `drop --force` can discard working content; inspect its dry-run output and the affected resources first. Recovery backups preserve Git history and discarded filesystem content before destructive work. Keep these backups until the result is verified. A backup is recovery evidence, not authorization to overwrite unrelated work.

Legacy creation synchronization journals remain under the workspace Git common directory as `vcm/*.sync`. New creation uses local trunks and never writes these journals. Their presence blocks mutation without deleting or modifying evidence. Use the previous binary to finish or discard the interrupted creation; preserve Git history and working content throughout recovery.

Workspace publication is intentionally non-atomic across repositories. `vcm push` publishes canonical trunks; `vcm publish <change>` publishes every selected ready, clean Change branch to `refs/heads/<Change tag>`. Both preflight the complete selection, freeze source SHAs and destinations, reject local drift, and push exact object IDs in child dependency order with root last. Updates must be fast-forward; neither operation force-pushes or deletes remote branches. A remote update race, server rejection, or transport failure can occur after earlier children have been published. Inspect the reported repository, resolve the remote failure without rewriting already-published history, and rerun the same publication command. Reports distinguish completed, blocked, and pending repositories; destinations already matching their frozen sources are idempotent. Publication previews do not contact remotes.

Ordinary drop also rejects ignored filesystem content. Forced drop preserves discarded content in recovery backups, but still rejects foreign nested Git repositories; relocate those repositories explicitly before retrying.

Use `vcm check` to inventory dirty registered worktrees, unfinished Git operations, and local branches or worktrees that are not authorized by the configured trunks and live VCM state. Remote-tracking and recovery refs are not pruning targets. Missing resources and ownership mismatches require manual investigation; VCM protects live-state branches and paths when their registration disagrees with current configuration.

Use `vcm prune --dry-run` to review cleanup candidates. If any state file cannot be validated, pruning remains incomplete and produces no actions because that state may authorize resources that VCM cannot safely identify. A real prune requests approval for every reset, worktree removal, and branch deletion. Retained checkout resets discard tracked and ordinary untracked content at the current `HEAD` but preserve ignored files. Unexpected worktree removal deletes the entire worktree, including ignored files. Branches are deleted only after worktree processing and only if their object ID still matches the audited value. Prune creates no recovery archive or recovery ref: each confirmation is authorization for irreversible deletion, so preserve anything needed before answering yes.

VCM only removes resources it recorded as owned. If paths, branches, or worktrees were replaced manually, restore the expected ownership or resolve the discrepancy explicitly. Never delete an unfamiliar path merely because its name resembles a Change.

If adopting a repaired merge gate after committing configuration has advanced a canonical trunk, and integration has not begun, VCM resets the Change to ready and archives the old gate outcomes. Run the reported `refresh` command, then retry `merge`; the merge subject and retention choice are preserved. Gates run again against the refreshed sources. Without a baseline change, adoption preserves completed gates before the changed definition and invalidates only the affected suffix.

A failed merge hook may leave a clean committed source repair. Adopting its replacement before integration resets verification to ready and archives previous gates, so retrying merge validates the repaired source without losing the recorded subject or retention choice. Prepared or applied integration still blocks this reset.
